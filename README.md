## 1. Bottom line

1. **The manuscript's headline funnel is not the RL pipeline's.** 30,000 / 2,862 / 3,376 / 25 / 85 appear only in the edit-family notebook's printed output; 514 appears nowhere except as 3,376 - 2,862. The RL data give 7,500 generated and 750 final-ranked over 75 visits (190 rows exported).
2. **46% of the exported final rows are failed dockings.** 87 of 190 carry the -7.000 placeholder; the placeholder enters the per-visit composite score and the exported rank. No structure has a valid top 10 (2 to 9 valid rows each, median 5).
3. **The exported rows do not satisfy the pipeline's own property-range gate.** The notebook's function rejects 48 of 190 (46 on N+O, 40 on TPSA) that are stored as passing. The descriptors in the table are identical to what the gate computes, so the cause is not a descriptor mismatch; the run-time gate was not the function-and-thresholds in any archived notebook (inference), and the run-time configuration is not archived.
4. **The manuscript mixes two code lines** (RL pipeline and edit-family notebook) and states "GCN-PPO" where 58 of the 75 visits resolved to GraphSAGE.
5. **The data cannot be tied to a notebook version.** The exported tables carry no configuration hash; most notebook differences (entropy coefficient, episode length, timeout, scaffold filter) cannot be told apart from the tables.

Taken together: the computation is mostly sound where it can be regenerated (scores, thresholds, counts of the 75 visits), but the thesis cannot yet claim that the reported candidates passed the reported filters, and several manuscript numbers cannot be traced to any file.

## 4. Defects in my own code and deliverables (recorded, not repaired)

* The roster preview's "few protein neighbours" threshold (150) is uncalibrated; in the 9b517a30 run it flagged all eight real inhibitor ligands.
* A saved policy is adopted by vocabulary size against the post-acquisition library, so a library that grows during acquisition discards the learned head (9b517a30: kept 0, added 256, dropped 241). Visits 475-477 therefore did not continue the earlier policy.
* `gate_diff.json` key `pass_if_gate_used_HBA_instead_of_nO` (165) ignored TPSA; the correct combined figure is 128 of 166 native rows.

* The earlier discrepancy log (D01-D49) and revised manuscript and progress report were not re-traced end to end here; Step 4 traced the student's manuscript and my progress report.

## 5. The three highest-priority fixes (not made)

Ordered by how much of the thesis rests on them. Each has the reason, the minimum evidence that it is done, and what it does not fix.

### Fix 1. Establish and archive run-time provenance for the 75 visits and 190 rows
**Why first.** The thesis is "judged on reproducible computation". Today no exported number can be tied to a notebook version, a configuration or a seed. Step 3 could not tell which of two config groups ran; Step 5a could not
decide whether the gate failures are a bug or a different gate, because the run-time configuration is not archived. Every other finding is ambiguous until this is settled.
**What to do.** (a) Obtain the notebook as it ran (Colab session history or the saved notebook for the 5 to 26 Sep 2026 campaign) and the per-visit result files for all 75 visits, not only the 19 top-10 files; (b) write a configuration hash, the CONFIG itself and the seed into every exported table
and every W&B run; (c) decide, in writing, which code line the thesis describes (RL pipeline) and move edit-family content to a separate, labelled section or drop it.
**Done when.** One archived notebook plus one config file regenerates the funnel counts of all 75 visits and the 190 exported rows, and the gate question of Step 5a is answerable.
**Does not fix.** The failed dockings or the ranking.

### Fix 2. Make a failed docking impossible to enter a score or a rank
**Why second.** It affects almost half of the exported rows and every ranking built from them; it is also the standing rule of this project. Today a failure is stored as -7.000 in the score field, feeds the per-visit min-max normalisation and the composite, and sits in the top 10 (87 of 190). The code also
returns -7.0 for an unparsed Vina output under an ordinary `vina_cli_e<N>` label, which the failure flag would miss.
**What to do.** Store a failure as missing (NaN) with an explicit status, exclude missing rows before any normalisation, mean or rank, label the unparsed-output case as a failure, and fix the NaN-composite behaviour for repaired rows (compute the diversity bonus for them, or rank them on a documented rule).
Then re-run the visits (the 560 unexported candidates are not recoverable) and report valid-row counts next to every statistic.
**Done when.** A test that injects a failed docking shows it absent from the composite, the rank and every summary; every table reports valid counts; no structure's top-10 contains a placeholder.
**Does not fix.** The gate or the manuscript's untraceable numbers.

### Fix 3. Enforce the property-range gate on final rows and record its thresholds with every output
**Why third.** After Fix 1 tells which gate ran, the gate must be a recorded, tested rule. Today 48 of 190 final rows fail the pipeline's own function, `hard_filter_passed` says "pass" for a different, narrower test, and the JAK1 headline (-10.39) is a gate failure.
**What to do.** Decide, with the professor, the intended thresholds (N+O < 9 strict versus <= 9; TPSA < 129.9), apply the gate as a final check on every exported row, write the thresholds and the gate outcome into the table, and rename or split `hard_filter_passed` so that it states what it covers.
Re-derive the headline per-structure scores on valid, gate-passing rows (the four structures in Step 5b change).
**Done when.** Re-running the gate over the exported table reproduces the stored flags for 190 of 190 rows.
**Does not fix.** Which rows are the best candidates scientifically; that requires Fix 2's re-run.
